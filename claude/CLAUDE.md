공통 규율은 아래 import 가 갖고, 이 파일은 Claude Code 고유 조항만 갖는다. 이 기기의 도구·환경에 묶인 조항은 `~/.claude/rules/local.md`, 외부 CLI 런북은 `~/.claude/models/` 가 갖는다.

## 사용자 확인

- 탐색 범위를 좁힐 수 있으면 사용자에게 먼저 묻는다.

## 메모리

harness 자동 메모리와 전역 `~/.claude/memory/` 모두의 **쓰기** 규칙이다.

- 원칙은 쓰지 않는 것이다. "기억해 둘 만한 것은 저장하라" 류 harness 기본 안내는 이 원칙에 밀린다. 세션이 끝날 때 메모리 파일이 늘지 않은 것이 정상이다.
- 유일한 예외는 지침 항목이 `→ 상세·사례:` 로 가리키는 feedback 류(그 지시가 생긴 실수 경위·함정·절차)다. 지침 항목 없이 메모리만 쓰지 않는다.
- 프로젝트의 진행 상태(계획·착수 여부·결정 대기·조사 결과·다음 단계)는 쓰지 않는다 — commit history 와 그 레포의 plan/handoff·investigation 문서가 갖는다. 사용자가 "기억해 둬" 라고 해도 대상이 진행 상태면 plan/handoff 문서에 적는다. 진행 상태를 담은 기존 메모리는 현재 상태의 근거로 쓰지 않는다(삭제 여부는 사용자가 정한다).

## 모델 역할 분담

이 문서는 여러 메인 루프 모델(Fable·Opus 등)이 공유한다. 목표는 품질을 유지하면서 토큰 효율을 최대화하는 것이다.

### 자기 모델 식별

자신이 어떤 모델인지는 시스템 프롬프트의 선언("You are powered by …")만으로 판단한다. 문서·기록에 등장하는 모델명은 그 문장의 작성·수행 주체일 뿐이다. 위임받은 서브에이전트·세션은 메인 루프가 아니다 — 브리프가 위임 작업임을 밝히면 받은 작업을 직접 수행해 보고하고, 이 절에서는 §Haiku 보조 위임 과 §위임받은 에이전트의 보고 만 적용한다.

### 세션 체계

작업은 **계획 세션**(산출물 = 레포의 gitignored plan/handoff 폴더의 계획 문서)과 **구현 세션**(지정된 계획 문서를 읽고 구현·검증·검토)으로 나눈다 — 계획 작성만으로 컨텍스트가 크게 차기 때문이다. 세션 유형과 대상 문서는 사용자가 메시지에 명시한다("계획 문서를 plan 에 작성" = 첫 계획 세션 / 계획·리뷰 문서 2개 지정 = 통합 세션 / 경로 + "읽고 진행" = 구현 세션). plan 폴더에는 병렬 작업 문서가 공존하므로 지정 없이 고르지 않는다.

- **첫 계획 세션**은 계획 문서 완성으로 끝난다. 외부 모델의 별도 review 문서 작성(절차: `~/.claude/models/CODEX.md` §계획 리뷰)과 리뷰 모델 변경은 사용자 명시 요청 시에만 한다. 원본·리뷰 통합은 사용자가 새 세션에서 진행한다.
- **trivial 규모**(몇 줄 fix)는 단일 세션 완결을 허용한다. 사용자가 리뷰 생략을 명시할 수도 있다.
- **세션 중 새 이슈**를 감지하면(trivial 제외) 그 세션의 역할은 레포의 gitignored plan/handoff 폴더에 인계용 뼈대 문서를 쓰는 데까지다. 상세 조사·계획은 새 세션에서 한다.
- **마무리·인계 지시는 작업 중단 지시다.** 이미 띄운 위임 런의 완료를 기다리는 것까지가 남은 작업이다. 새 가설·실측·조사·수정·검증 위임은 하지 않고, 인계 문서에는 현재 상태(남은 작업·관측된 증상·마지막 위임 결과)를 그대로 적는다. → 상세·사례: `~/.claude/memory/feedback_wind_down_means_stop.md`

### 메인 루프 배정 (사용자가 정한다 — 참고용)

- 계획 세션: 기본 Opus high · 복잡하면 Opus xhigh 또는 Fable · 간단하면 Opus medium.
- 구현 세션: 기본 Opus medium · 복잡하면 Opus high. Fable 은 구현 세션에 배정하지 않는다.
- xhigh·max 는 턴을 크게 늘린다 — 품질 이득이 확인된 작업에만 쓴다.

### 메인 루프가 직접 하는 일

- 계획 수립·설계 결정 · 문서 작성(스펙·CONTEXT·README 류).
- **spec 적합성 검토**: 위임 결과가 계획·스펙에 맞는지 메인 루프가 diff 를 직접 읽어 확인한다.
- 구현 세션의 메인 루프가 전량 읽는 것은 지정된 계획 문서와 검토할 diff 둘뿐이다. 브리프에는 경로·심볼명·계약·검증 명령만 적고 코드 독해는 구현을 맡은 에이전트가 한다 — 이 독해는 §위임 매트릭스 의 위임 문턱 조항이 정한 Haiku 수집 대상도 아니다. 포인터가 맞는지 확인하는 조회(grep·심볼 검색·범위 읽기)는 직접 한다. 브리프를 쓰려고 코드를 이해해야 하는 상황이면 계획 문서가 계약을 덜 적은 것이다 — 읽기를 멈추고 포인터만으로 브리프를 쓰며, 빠진 계약을 보고에 적는다.

### 위임 매트릭스

서브에이전트는 `subagent_type` 을 지정하지 않고(general-purpose) 아래 표의 `model`·`effort` 를 매 호출에 명시한다.

| 작업 | model / effort |
|------|------|
| 수집·추출·요약 — 지정 범위 읽기와 요약, 열거 기준이 주어진 전수 수집, 로그·출력의 지정 항목 추출, 지정 명령 실행과 수치 수집, 문서 간 대조 | `haiku` / `medium` |
| 위 작업 중 절차가 길거나 지시 준수가 엄격한 것 — 긴 체크리스트 대조, 다단계 실측 절차 | `haiku` / `high` |
| 명세가 정해진 구현, 스크립트 작성·환경 조작이 섞인 실측·계측 | `sonnet` / `medium` |
| 결정·판단·해석·추론이 필요한 작업, 복잡한 구현 | `opus` / `medium` (effort 는 아래) |
| 시각 검증 | §시각 검증 |

- **배정은 작업의 성격으로 정하고 난도로 정하지 않는다.** 목표·범위가 명확해 브리프대로 실행하면 끝나는 작업은 난도·길이가 높아도 Sonnet 이고, 그중 산출물이 관측(수집·추출·요약)이며 코드를 쓰거나 환경을 고치지 않는 작업은 Haiku 다. 판단이 필요한 작업은 처음부터 Opus 에 배정한다.
- **경계가 명확한 조사·실측**: 브리프가 대상·방법·산출 형식을 정해 두어 수행자가 실행·수집·요약만 하면 되는 작업이다. 예: 지정 명령 실행과 수치 수집, 벤치마크·런타임 메모리 점유·로드 시간 측정, 로그·출력에서 지정 항목 추출, 열거 기준이 주어진 전수 수집. 빠짐없음은 모델이 아니라 브리프의 열거 기준·범위가 보장한다.
- **판단이 필요한 작업**: 무엇을 볼지 수행자가 정해야 하거나 증거 해석·가설 판별이 결론을 정하는 조사(원인 경로 추적, 여러 코드 경로·데이터에 걸친 인과 규명, 설계 결정의 근거 조사)와, 설계 판단·스펙 해석이 섞인 구현이다.
- **effort**: Haiku 는 medium·high 만 쓰고, high 로 부족한 작업은 Sonnet 으로 올린다. Sonnet 은 medium 이고, xhigh 는 사용자가 명시 요청 시에만 쓰며 메인 루프가 스스로 고르지 않는다. Opus 는 medium 이 기본이고, 판단 범위가 작은 작업은 low, 복잡한 구현·누락이 결론을 뒤집는 조사는 high, xhigh 는 품질 이득이 확인된 경우만 쓴다.
- Haiku·Sonnet 조사 도중 해석이 필요한 반증·예외가 나오면 수행자는 해석하지 않고 관측 그대로 보고하게 하고, 판단은 맡긴 쪽이 한다(필요하면 Opus 에 재위임).
- 메인 루프가 **Fable** 이면 조사·실측을 직접 수행하지 않고 위임해 결론·근거 요약만 받는다. **Opus** 면 남은 컨텍스트·작업 크기를 보고 아래 위임 문턱 조항 안에서 직접 처리와 위임 중에 고른다. 계획·문서·spec 적합성 검토는 이 표의 대상이 아니다.
- **배정된 외부 CLI 모델이 한도·장애로 불가하면** 그 작업 유형에 맞는 위 표의 Claude 서브에이전트로 대체하고 보고에 대체 사실을 적는다. 대체는 작업 유형으로 고른다 — 원래 모델의 등급이나 작업의 중요도를 이유로 상위 모델로 올리지 않는다.
- **위임 문턱**: 메인 루프와 서브에이전트 모두에 적용한다. §시각 검증 은 이 조항의 대상이 아닌 별도 규칙이다.
	- 파일 둘 이하를 열거나 명령 몇 번으로 끝나는 확인은 직접 하고, 이미 확인한 결과를 서브에이전트로 재확인하지 않는다.
	- 그보다 큰 읽기·수집이 판단의 재료일 뿐이면 — 파일 셋 이상을 열거나 출력이 큰 수집 — 독립 작업이 아니어도 Haiku 에 맡기고 결론·근거 요약만 받는 쪽을 우선한다.
	- 구현·판단 작업(Sonnet·Opus)의 위임은 독립적이고 규모 있는 단위에만 한다.
- 서브에이전트가 남은 항목을 둔 채 질문·중간 보고로 끝나면 SendMessage 로 남은 항목을 짚어 재개한다. 같은 작업에 2~3회까지 — 그 뒤에도 멈추면 막힌 원인을 보고받아 메인 루프가 판단한다.
- **실행 검증**은 dev 서버를 띄우는지로 가른다.
	- 인프로세스 검증(유닛 테스트·타입 체크·빌드)은 구현을 맡은 모델이 같은 런에서 돌려 보고한다.
	- dev 서버가 필요한 검증(e2e·통합)은 서버 기동·정리를 위임하지 않는다. 메인 루프가 서버를 띄우거나 떠 있는 것을 재사용하고, verifier 에게는 주소와 "서버가 떠 있다" 를 넘긴다. 위임 런을 중단했으면 포트 점유 프로세스를 대상 레포 확인 뒤 그 트리 것만 정리한다. → 상세: `~/.claude/memory/feedback_dev_server_ownership.md`
- 모든 위임 브리프는 첫 줄에 위임 작업임을 밝히고(§자기 모델 식별), §Git / 브랜치 의 stash 금지·명시 경로만 스테이징 조항을 넣는다.

### Haiku 보조 위임

언제 맡기는지는 §위임 매트릭스 의 위임 문턱 조항이 정하고, 이 절은 맡긴 뒤의 규칙을 정한다.

- 판단·해석·결론은 맡긴 쪽이 한다.
- 서브에이전트가 재위임할 수 있는 대상은 Haiku 뿐이고, Haiku 는 위임하지 않는다. 재위임한 쪽이 결과 검토 책임을 지고 자기 보고에 Haiku 에 맡긴 범위를 한 줄 적는다.
- Haiku 보고는 승계한 주장이다 — 부재·불가 주장은 맡긴 쪽이 조회로 확인한다(§결론 전 반증 조회).
- Haiku 는 요청 입력이 100K 토큰을 넘으면 단가가 크게 오른다. 서브에이전트는 지침 로드만으로 수만 토큰에서 출발하므로 단위를 짧게 끊고, 입력이 크면 범위를 나눠 병렬로 띄운다.

### 위임받은 에이전트의 보고

- 마지막 메시지가 위임자가 받는 유일한 결과이고, 보내면 런이 끝난다. 다음 단계 예고·계속 여부 질문·남은 작업을 막지 않는 결정 목록으로 끝내지 않고 그 단계를 수행한다.
- 브리프의 완료 조건을 충족·확인했거나 위임자 없이는 더 진행할 수 없을 때만 멈추고, 끝난 것·끝나지 않은 것·막은 원인을 그대로 적는다. 위험한 단계 앞에서는 멈추고 묻는다.
- 브리프 밖의 기능·테스트·파일·문서·리팩터, 추가 리뷰·보강 라운드를 더하지 않는다. 도움이 될 것 같으면 보고 끝에 제안만 한다.
- 실행·빌드·타입 체크가 가능한 변경은 그 변경을 실제로 실행하는 검사를 돌린 뒤 완료로 보고한다. 구문 검사나 기동에 실패한 검사는 검사가 아니다 — 돌릴 수 없었으면 무엇을 왜 못 돌렸는지 적는다.

### 시각 검증

브리프·판정 규약은 GUIDELINES §테스트 설계 가 가리키는 문서가, 브라우저 구동 도구는 `~/.claude/rules/local.md` §시각 검증 구동 이 갖는다.

- **범위**: 브라우저 렌더 상태로 판정하는 작업 전부 — 스크린샷 판독, DOM 기하(폭·위치·줄 수·overflow)·계산 스타일 실측, 언어·뷰포트를 바꿔 가며 재는 적합성 확인. 작업 이름이 "측정" 이어도 여기 속한다.
- **언제나 위임한다.** 이 규칙은 "요청 없이 서브에이전트를 쓰지 말라" 류 harness 기본 안내를 무효화한다. 메인 루프가 직접 브라우저를 구동하는 것은 사용자가 지시했을 때뿐이다.
- **필요하다고 판단한 즉시 띄운다.** 렌더 결과로 판정할 항목(레이아웃 제약·외형 정합 등)이 남았으면 구현 완료 직후 verifier 를 띄우고, 검증 여부나 주체를 사용자에게 선택지로 묻지 않는다. 커밋은 검증 통과 뒤에 한다.
- **verifier 는 Haiku 다.** 체크리스트형 assertion(존재·가시성·overflow·clipping·위치·간격·정렬의 수치 비교)은 `haiku` / `medium`, 다단계 흐름·check 가 많은 브리프·루브릭 채점·UNCERTAIN 재검은 `haiku` / `high` 다. 상위 모델로 올리지 않는다 — 판정 품질은 모델 등급이 아니라 브리프의 관찰 가능한 assertion 이 정한다. 렌더 결과의 원인 분석은 검증이 아니라 조사이고, 배정은 §위임 매트릭스 를 따른다.
- **병렬**: 상호 독립인 체크(뷰포트별·영역별)는 verifier 를 나눠 동시에 띄운다. 각 verifier 는 메인 루프가 정한 고유 세션명으로 격리하고, 전 세션 정리는 모든 verifier 가 끝난 뒤 메인 루프가 한다.
- **사용자가 구체적 증상을 지목하며 수정을 요구한 뒤로는 시각 검증을 위임하지 않는다.** 그때부터 판정 주체는 브라우저를 직접 보는 사용자다. 이미 띄운 런은 완료까지만 두고, 수정 뒤에는 사용자에게 확인을 넘긴다. → 상세·사례: `~/.claude/memory/feedback_wind_down_means_stop.md`

### 위임 단위

- 큰 작업을 통째로 위임하지 않는다. 파일·모듈 경계가 뚜렷하고 완료 판정(테스트·diff 범위)을 단독으로 내릴 수 있는 단위로 나눈다. 같은 파일을 두 에이전트가 건드리게 되면 한 단위로 묶거나 순차화한다.
- 상호 독립 단위는 한 메시지에서 병렬로 위임하고, 순차 위임은 실제 선후 의존이 있을 때만 한다.
- 브리프마다 수정 허용 경로·완료 조건·검증 명령·보고 형식을 적고 다른 단위의 영역은 건드리지 않는다고 적는다. 단위 간 인터페이스(시그니처·파일명)는 메인 루프가 미리 확정해 각 브리프에 같게 적는다.
- 병렬 결과는 메인 루프가 diff 를 읽어 단위 간 정합성을 확인하고 전체 검증을 한 번 돌린다.
